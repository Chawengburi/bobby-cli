# 13 Spec: Skill Architecture — one single-file skill per CLI, hand-maintained

> **Status: ACCEPTED (2026-07-18).** This revision **supersedes and retires**
> the previous hub-and-spoke + `schema render` design (accepted 2026-07-17,
> retired 2026-07-18 before any implementation started — no code existed).
> The owner's direction, after reviewing real-world prior art, is a single
> hand-maintained SKILL.md and no generator. The retired design survives in
> git history and in § "Retired: the renderer" below for context.

> Decision context: 2026-07-18 discussion. Prior-art research performed the
> same day:
>
> - **gog** (`openclaw/gogcli`, formerly steipete's) — one ~8.9 KB SKILL.md
>   covering all of Google Workspace (Gmail, Calendar, Drive, Sheets, Docs,
>   Contacts, …). It never splits per module because it never *enumerates*:
>   thematic sections (Fast Path / Safety / Auth / Common Reads / Writes)
>   with a few representative examples per service, plus runtime discovery
>   (`GOG_HELP=agent gog --help`, `gog schema --json`) for everything else.
> - **Google Workspace official CLI** (`googleworkspace/cli`) — the opposite
>   extreme: 60–100+ SKILL.md files (per-service + helpers + personas +
>   recipes), auto-generated by `gws generate-skills`.
>
> Both patterns are viable in the wild. The deciding factor is **scale**:
> gog has 100+ commands (a full table is impossible → runtime discovery);
> Google generates because 100+ hand-written files would rot. bobby-cli has
> **8 tools** (projected ~15–20 with uploader/n8n). At that scale a complete
> command table fits in one small file — post-spec-12 diet, both domains
> together land ≤ ~2.5 KB, roughly a third of gog's single file. Splitting
> saves ~zero context and adds a file hop; generating adds a subcommand to
> maintain for a table that changes a few times a year.

Builds on: [09-spec-agent-tool-schema.md](./09-spec-agent-tool-schema.md)
(`schema/tools.json` stays the machine-readable source of truth),
[11-spec-claude-code-skill.md](./11-spec-claude-code-skill.md) (the current
skill this revises), [12-spec-agent-legible-output.md](./12-spec-agent-legible-output.md)
(the diet that makes a complete single file this small).

## Design

### 1. One SKILL.md per host — sections, not files

```
<skills dir>/bobby-cli/
└── SKILL.md      # the whole skill: policy + one section per domain
```

The single file carries:

- **Shared mechanics** every domain uses: the `--json` envelope with
  `code`/`hint` (spec 12), quoting/stdin rules, auth recovery ("follow the
  `hint`"), token safety.
- **One short section per domain** (memory, auth, future uploader/n8n):
  the command-template table for that domain. Spec 12 is what keeps these
  sections thin — domain semantics live in the CLI's `code`/`hint`, not in
  per-domain prose.
- **Project policy** (recall-at-start, store-don't-ask, tag taxonomy) —
  host-specific, hand-written.

Target budget: ≤ ~2.5 KB today (spec 12 success criterion 3); soft ceiling
~8 KB (see § 3).

### 2. Drift control without a generator: the same-change rule

The retired renderer existed to stop skill tables drifting from the
installed CLI. Without it, drift control is the **same-change rule**,
mirroring spec 09's existing manifest discipline:

> Any command or flag change updates `schema/tools.json` **and every
> deployed SKILL.md command table** in the same change.

Record this in `DEVELOPMENT.md` next to the existing tools.json rule.
Deployed copies today: the chawengburi repo's
`.claude/skills/bobby-cli/SKILL.md`; after the openClaw migration, also
`~/.openclaw/workspace/skills/bobby-cli/SKILL.md`.

This is an **accepted trade-off**, chosen with eyes open at the current
scale (8 tools, a few changes a year, one maintainer). The revisit trigger
is § 3.

### 3. Growth path: what happens when the file gets big

Reconsider (in this order) when SKILL.md exceeds ~8 KB, or when a domain
lands that most sessions never use:

1. **gog-style compression first**: shrink rarely-used domains to a few
   representative examples + one line pointing the agent at
   `bobby-cli/schema/tools.json` for the full parameter schema (the
   manifest is already the machine-readable reference — spec 09).
2. **Split reference files second**, and only for the rarely-used domain.
3. **Revive generation last** — the retired renderer design (git history of
   this file, 2026-07-17 revision) is the blueprint if hand-maintenance
   actually rots in practice; Google's `gws generate-skills` proves the
   pattern at scale.

### 4. One skill per CLI — unchanged, and now explicit for openClaw

New bobby-cli capabilities are always new tools in `tools.json` + a new
section in the **same** SKILL.md — never a new skill. (Restates spec 11's
naming rationale as a rule; unchanged from every prior revision.)

**openClaw consolidation (decided 2026-07-18):** the existing separate
openClaw skills that wrap what bobby-cli now does — `login`
(`~/.openclaw/workspace/skills/login/SKILL.md`), forget/credential-reset,
and any other session-memory-adjacent skill — are **collapsed into the one
bobby-cli skill** during the openClaw migration. Per-host differences stay
confined to that file's shared prose:

- every command carries `--profile discord-<userId>` (spec 10 dispatch);
- `/login` keeps its current DM UX with `bobby-cli auth login` underneath,
  non-interactive via `BOBBY_CLI_EMAIL`/`BOBBY_CLI_PASSWORD` env vars
  (never flags — argv is visible in the process list) plus
  `--profile`/`--label` per user; the device-code upgrade (D4) later
  changes only what `/login` says to the user.

A single file makes the deploy story trivial: the migration ships one
file. Details belong to the openClaw migration spec.

### 5. Skill description budget

A multi-domain skill's frontmatter `description` must enumerate every
domain or auto-triggering breaks for the unlisted ones. Harness listing
caps description at ~1,536 characters — with N domains, write it as a
compact enumeration ("…via bobby-cli: memory (recall, remember, append,
forget, show — list recent), auth (login, show, forget)…"), most-used
domain first. Reviewing the description is part of adding a domain.

## Retired: the renderer (`bobby-cli schema render`)

The 2026-07-17 revision specified a hub-and-spoke layout (`SKILL.md` +
generated `auth.md`/`memory.md`) produced by a `schema render` subcommand
with generated-block markers, manifest-order rendering, orphan handling,
and an `x-skill-exclude` manifest field. Retired 2026-07-18 before
implementation: at 8–20 tools the generator is more machinery than the
table it generates. Consequences of retirement:

- `x-skill-exclude` is **not** added to `schema/tools.json` (spec 09's
  mention is removed); there is no `schema_render` tool entry.
- The `rendered` envelope code does not exist.
- The manifest-`version` = CLI-version rule (spec 09) **survives** — it
  closes a real drift bug (manifest said 0.1.0 against a 0.2.x CLI)
  independently of any renderer.

## Success criteria

1. **Single file** — `<skills dir>/bobby-cli/` contains exactly one
   SKILL.md and no per-domain `.md` files; the file covers all 8 current
   tools in per-domain sections.
2. **Budget** — `wc -c` ≤ ~2.5 KB today; the spec 11 trial protocol passes
   with the rewritten file (spec 12 success criterion 3).
3. **Same-change rule recorded** — `DEVELOPMENT.md` names both
   `schema/tools.json` and deployed SKILL.md tables in its
   command-change checklist.
4. **Description** — frontmatter enumerates every domain (§ 5).

## Open questions

1. The exact ~8 KB / rarely-used-domain revisit threshold is a judgment
   call — revisit when uploader lands, not before.
2. Whether openClaw's copy should be byte-identical plus a per-host
   appendix, or a separately maintained variant — decide in the openClaw
   migration spec (single file makes either cheap).
